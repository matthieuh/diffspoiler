# Real-page QA and performance check (2026-10-20)

Automated run, headless Playwright Chromium 1.57 with the built extension loaded unpacked
(`apps/extension/.output/chrome-mv3`, fresh profile per run), anonymous, public pages only, viewport 1440x900.
No account or token was used, so the private-repo and logged-in paths are in the manual checklist at the end.
Scripts live outside the repo (session scratchpad: `qa-lib.cjs`, `qa-gitlab.cjs`, `qa-github.cjs`, `qa-prof.cjs`, `qa-shift*.cjs`).

Method: layout shifts via `PerformanceObserver('layout-shift')` (sources checked for the `diffspoiler-badge` node), a
no-extension baseline run of the same pages, geometry snapshots around the badge, widget "ready" = the `Total` row
rendered in the badge's shadow root, API start = first request of the extension's own query (GitLab: GraphQL post
without `operationName`; GitHub: `api.github.com/repos/...`). Main-thread cost via CDP `Profiler` (200 us sampling).

The < 300 ms target for a cold normal page is not met here: the cold path is two sequential round trips and a single
GitLab GraphQL call already measures 0.39 s with curl from this machine (`gitlab-api.md`). The extension's own CPU time is
a few ms, so the floor is network latency; the cache-hit path (one head request) is 150-420 ms for the same reason.
The GitHub huge case is 30 file pages of 100 (the REST maximum); it is bound by request count and latency.
Single machine, single network, 1-3 samples each: indicative, not a benchmark.

## Layout shift

Shifts are page-wide and mostly GitLab's/GitHub's own. The badge node itself is never a shift source. Comparing with a
no-extension baseline:

- GitLab normal MR: the one 0.0009 shift in the meta line shows up with the extension on commits only, but geometry
  snapshots (children of the description row at badge insert and at ready, and with the badge hidden) are identical:
  nothing moves because of the badge. PASS in practice.
- GitLab huge MR, Changes tab: the toolbar (`.rd-app-settings`) hydrates and widens in both runs (0.068 without the
  extension, 0.090 with). The badge moves from the meta line into that right-aligned toolbar next to `.diff-stats`
  and widens it by 80 px (left edge 1052 -> 972 with it hidden vs shown), so about 0.02 of the shift is attributable.
  Page total with the extension is about 0.104 vs 0.075 without.
- GitHub conversation and commits tabs: with the extension a 0.0057 (conversation) / 0.0024 (commits) shift on
  `PageHeader-Navigation` appears on every load; it is absent from the baseline runs. The badge wraps onto its own
  line under the long meta text and pushes the header down. Tiny but non-zero.
- Other shifts (0.0765 / 0.2346 on the GitHub conversation timeline avatar, 0.0872 on the GitLab huge overview
  timeline) also occur without the extension; the 0.2346 is a one-off first-load outlier (0.0765 on all later loads).

Repro: load each page above with and without the extension, compare `layout-shift` entries and their `sources`.
Expected: no shift sources moved by the badge; observed: the above. No production code was changed (task rule).

## Popover clipped on the right edge

At 1440 px wide the popover (left-aligned to the 56 px host, 276 px wide) runs off screen when the badge sits near the
right edge, hiding the additions/deletions columns:

- GitLab Changes tab (badge x=1224): popover right edge 1500 > 1440, 60 px cut (`gitlab-huge-mr-changes.png`).
- GitHub Files tab (badge x=1360): popover right edge 1636 > 1440, 196 px cut, only the labels remain visible
  (`github-files-tab-popover-clipped.png`).

Expected: popover fully on screen (flip to right-aligned, `right: 0`, when it would overflow). Fixed afterwards, see "After fixes".

## Main thread: per-frame anchor lookup (huge MR Changes tab)

Profile over load + 25 wheel scrolls of 1,500 px (about 10 s, 3,285-file MR): 1,904 ms non-idle total, of which all
`content.js` functions together 54.2 ms (2.8%). The hottest is the minified `D` = `rendered()` (`checkVisibility`) at
44.5 ms self time, i.e. about 0.4% of the window. Long tasks on the page: 283 + 84 ms with the extension on first load
vs 119 + 94 + 152 ms without (page-driven, same order); no long-animation-frame entry has an extension script. Result:
no freeze risk observed; the rAF coalescing keeps it to one lookup per frame. Worth revisiting only if the lookup grows.

## After fixes (2026-10-20)

Fixes: popover right-aligns when it would overflow the viewport; the head and the files requests now start together
(GitHub: `fetchFiles` reuses the head request and fetches page 1 concurrently with it). Rebuilt (`content.js` 18.2 KB),
same Playwright scripts, same machine, GitLab `!263303` (normal MR), fresh profile per run, 3 cold runs.

| Case | Before | After |
|---|---|---|
| GitLab normal, cold (first API request -> widget ready) | 800 ms | 373 / 637 / 1,055 ms (requests: head + files, now concurrent) |
| GitLab normal, revisit (cache hit) | 228-376 ms | 273 / 277 / 428 ms |
| Popover on GitLab huge MR Changes tab (badge x=1224) | right edge 1500 > 1440 | spans 1004-1280, right edge aligned to the badge (`right: 0`), fully on screen |

- Cold latency is now bound by the slower of the two requests instead of their sum; the spread (373-1,055 ms) is network
  variance on a single connection, 3 samples, indicative only. The < 300 ms target is still not reliably met when a single
  GraphQL call already costs 0.39 s from this machine.
- GitHub was not re-measured: the anonymous quota was at 2/60 (`x-ratelimit-remaining`), below the 10-request floor.
  GitHub cold path is now 2 requests for a small PR (pull and files page 1 in parallel) instead of 3 sequential ones, and
  30 + 1 requests for the 6,369-file PR with pages 2..30 at concurrency 6; the 3.86 s figure above is not updated.
- Side effect of the concurrent start: on a cache hit the files request is already issued. Later fix: the files fetch
  gets an abort signal that is fired on every exit except a cache miss, and GitHub schedules no page 2..n once aborted,
  so a revisit costs the head request plus at most page 1 already in flight. An aborted fetch rejects instead of
  returning partial data. The revisit measured above (one `files` request on GitLab) predates this and was not re-run.

- The GitLab UI was served in French; irrelevant to the extension.

## Manual checklist (needs your accounts)

1. Load unpacked: `pnpm build`, Chrome `chrome://extensions`, Developer mode, Load unpacked, pick
   `apps/extension/.output/chrome-mv3`. Open a PR and an MR: bar appears next to the `+/-` counter.
2. GitLab logged in (session + CSRF path): open a private MR you can see; bar on every tab; Total equals the page
   counter. Open a private MR you cannot access: the widget must stay hidden, no console error.
3. GitHub private PR without a token, logged out of github.com: bar shows the dashed `auth-required` state; hover it,
   click "Open options": the options page opens in a tab.
3b. GitHub private PR without a token shows the bar (session fallback): logged in to github.com, no token saved, open
   a private PR you can see: the bar appears and Total equals the header counter; the Network tab shows
   `pull/N/page_data/{header,diffstat,tab_counts,file_tree}` after the two `api.github.com` 404s.
4. GitHub private PR with a fine-grained token (read-only Pull requests, on that repo): save it in
   options, reload the PR: the bar appears and Total equals the header counter. Remove the token: it falls back to the
   session (bar shows if logged in to github.com; dashed auth-required state if logged out).
5. Dark theme on both sites, and a window narrower than ~1300 px: check the popover is not clipped (fixed, verify).
6. GitLab SPA navigation (Overview <-> Changes <-> another MR): the bar follows each route, no stale numbers from the previous MR.
